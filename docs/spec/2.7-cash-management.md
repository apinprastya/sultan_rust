# 2.7 Cash management — spec

Status: **agreed** (2026-11-19). §0 lists every decision as agreed with the user: K1–K7 and
K9–K26 as proposed, K8 changed to **yes** (nota photos, §2a), and K27 added (EDC settlement:
later).
Parent: `docs/plan.md` §2.7. Depends on 2.1 (cashier sessions, blind close, permissions,
overrides, audit, outbox), 2.6 (session effects §10, `POST /drawer/open`, close report `sales`
block), 2.5 §11 (balance payouts) and 2.3 §8 (cash rounding). 2.9 (money) and 2.11 (printing,
drawer kick) build on it later.

**What exists today** (so this spec only adds):
- Cashier sessions: open with opening cash, blind close with optional denomination counts, force
  close, stored close report, `GET /cashier-sessions[/{id}]` (2.1 §5).
- The close report's two blocks: the 2.1 block (`cash_sales`, `cash_refunds`, `cash_in`,
  `cash_out`, `expected_cash`, `over_short`, per-tender totals) and the 2.6 `sales` block
  (`core::sale::session_report`: cash received, change given, refunds, cash rounding, voids,
  returns, discounts, overrides, saved change, balance paid, payouts).
- `core::cashier_session::Movement::{CashIn, CashOut}` and `core::sale::SessionEvent::{CashIn,
  CashOut, Payout}` exist, but nothing creates cash in/out yet (`crates/server/src/movements.rs`).
- Balance payouts (`POST /customers/{id}/balance/payout`) lower expected cash and are in the
  report's `cash_out` (2.1 block) and `payouts` (`sales` block). No payout slip is printed.
- `POST /drawer/open` (F5): audited as `drawer.open` on the session, not counted in any report
  (2.6 §19 item 66).
- Permissions `cash.in`, `cash.out` (MaxAmount), `drawer.open`, `session.view_expected` exist.
  Seeds: Manager has `cash.in`, `cash.out` ≤ Rp 2 000 000, `drawer.open`,
  `session.view_expected`; Cashier has `cash.in` only.

## 1. Structure

```
CashReason (HQ master data) ── name, direction (in | out), active, sort, note_required
CashMovement (branch document) ── number, kind (in | out | drop), amount > 0, reason?, note?,
│                                 branch, register, cashier session, user, approved_by?,
│                                 reverses?, posted_at
│  └─ NotaPhoto (0..3) ── id, sha256, size, added_by, added_at, file on the branch node (§2a)
CashierSession (2.1, extended) ── + float_kept?, + opening_proposed?
ZReport (branch document) ── number, branch, business_day, seq, sessions[], figures (snapshot),
                             posted_at, user, approved_by?
```

- A cash movement is created **posted** (no draft). `in` needs a reason with direction `in`;
  `out` a reason with direction `out`; `drop` has no reason (an optional note).
- Numbers use the branch-local date (2.1 §1), with the 2.1 §5 retry rules:
  - Cash movement: `JKT01-R2-K-261119-01` (per register, per local day, 2 digits or more).
  - Z report: `JKT01-Z-261119-01` (per branch, per business day).
- Every cash movement and Z is **branch transactional data**: written with its audit entry and
  outbox row in one transaction, pushed to HQ (plan §1). Cash reasons are HQ master data,
  replicated to branches, so cash in/out works offline.

## 2. Cash in / out / drop

- Needs an **open session of the caller on this register** (`409 no_open_session`), like sales.
- **Fields:** kind, amount (Rp 1 up to `i64` range, whole Rupiah), reason (in / out), note
  (trimmed, at most 200 characters; required when the reason says so), and an optional
  `reverses` (K10).
- **Permissions:** `in` → `cash.in` (no limit); `out` → `cash.out` MaxAmount per movement;
  `drop` → `cash.drop`. All overridable at the till (`X-Override`, `context_ref` = the movement
  ID, value = the amount).
- **Effect on expected cash:** `in` adds, `out` and `drop` subtract (§4).
- The drawer opens (the kick comes with 2.11). It is not a no-sale drawer open (K22).
- **Reversal (K10):** `reverses` names a movement of the **same open session**, not reversed
  before, not itself a reversal. The new movement has the opposite effect, the same amount and the
  original's kind, reason and permission; it is shown as "reversal of …". Its note is required.
- **Seeded reasons** (Indonesian name / English), editable at HQ:
  - in: *Tambahan modal / uang kecil* (float top-up from the safe), *Lainnya* (other, note required)
  - out: *Belanja keperluan toko* (shop supplies), *Ongkos kirim / parkir* (delivery, parking),
    *Kebersihan / keamanan* (cleaning, security), *Lainnya* (other, note required)
- A reason in use is archived, never deleted (AGENTS.md). An archived reason is refused for new
  movements (`invalid_field`, `reason`) but still shows on old ones.
- **Slip (K7):** `GET /cash-movements/{id}/slip?lang=&width=&copy=`: branch header, CASH IN /
  CASH OUT / SAFE DROP, number, local time, register, cashier, approver, reason, note, amount in
  large text, "Received by / Diterima oleh" and "Given by / Diserahkan oleh" signature lines; a
  reversal prints REVERSAL and the original's number. A copy is free in the same open session,
  else `sale.reprint` (audited `cash_movement.reprint`). A balance payout gets the same slip
  layout from `GET /customers/{id}/balance/payouts/{entry_id}/slip`.

## 2a. Nota photos (K8)

- **What:** up to **3 photos** per cash movement (any kind; the "missing nota" flag concerns cash
  outs only). A photo is a record of its own, added after the movement is posted, so posting a
  cash out never waits for a camera or an upload.
- **Upload:** `PUT /cash-movements/{id}/photos/{photo_id}` (client UUIDv7), raw image body. The
  server reuses the product-image pipeline (`crates/server/src/product_image.rs`): the type is
  sniffed from the bytes (PNG / JPEG / WebP, else `422 invalid_image`), uploads over 10 MB are
  `413 payload_too_large`, and the image is scaled to fit **1600×1600** and re-encoded as JPEG,
  at most **400 KB** (larger than a product image, so a nota stays readable). The same
  `photo_id` with the same stored hash again → `200`, nothing changes; a fourth photo → `409
  photo_limit`.
- **Who:** at the till, the movement's own cashier while its session is open (no permission
  beyond the session). In the back office, anyone with `cash.out` at the movement's branch (any
  limit). Every photo writes an audit entry `cash_movement.photo`.
- **Append-only:** a photo is never deleted or replaced in P1; a wrong one is followed by a
  better one, and the note can say so.
- **Storage:** files on the node that owns the movement (branch or standalone), under the data
  directory: `attachments/<first 2 hex of sha256>/<sha256>.jpg`, owner-only (`0600`), written to a
  temporary file and renamed. The database row (`cash_movement_photo`: id, movement, sha256,
  size, added_by, added_at) is written with its audit and outbox rows in one transaction, after
  the file is in place. Same content twice is stored once (by hash). Backup / restore (2.12)
  includes the `attachments/` directory.
- **Sync:** the outbox carries `cash_movement.photo_added {photo_id, movement_id, sha256, size}`;
  the bytes go to HQ by a separate background push (`PUT /api/v1/sync/files/{sha256}`), so a large
  file never holds up transactional sync. Until the bytes arrive, HQ shows "photo not yet
  synced". (The sync worker itself is built with HQ + sync; 2.7 only stores and emits.)
- **Read:** `GET /cash-movements/{id}/photos/{photo_id}` (JPEG, `ETag`, `304`), for anyone who
  can read the movement.
- **Missing nota:** company setting `nota_flag_above` (Rp, default **100 000**, `0` = off) in
  `GET|PUT /settings/sales`. A cash out with amount ≥ the setting and no photo is "missing nota":
  a flag on the movement in lists, a filter `missing_nota=true`, and a count in the close report
  and the Z. It never blocks posting. A reversed cash out is not flagged.
- **Till capture:** the cash dialog, after posting (slip on screen) or on the movement list,
  offers **add photo**: a native file picker (`rfd`), or a frame from a USB webcam when one is
  found (a native capture crate behind a cargo feature `webcam`, so CI and headless tests build
  without it). No camera → only the file picker. A failed upload keeps the movement posted and
  the photo can be added again.

## 3. Float between sessions (K20)

- **Close:** the blind close screen asks, after the count, **"keep as float"**: default the
  session's opening cash, at most the counted cash. It is stored as `float_kept`. The rest
  (`counted − float_kept`) is "to the safe" and shown on the close report.
- **Open:** the open screen proposes the `float_kept` of this register's last closed session
  (0 if none). The cashier confirms or types another amount. A typed amount different from the
  proposal is stored as `opening_proposed` and the difference is shown on the open audit entry,
  the close report and the Z ("float difference").
- `float_kept` does not change expected cash or over/short: it is decided after the count.
- A force close (2.1 §5) asks the manager for the float the same way.

## 4. Expected cash and the close report

`expected_cash` (2.6 §10) becomes:

```
opening_cash + cash received − change given − cash refunds
             + cash_in − cash_out − drops − payouts
```

The close report (stored, unchanged after close) adds:
- `cash_in`, `cash_out`, `drops`: count + amount, and per reason (in / out).
- `drawer_opens`: count of no-sale opens (K22), `x_reports`: count of X reads (K12).
- `missing_nota`: count of cash outs flagged at close time (§2a).
- `float_kept`, `to_safe` (= counted − float kept), `opening_proposed` and the float difference.
- Reversals are netted into their reason's line and also counted on their own.

**Two blocks today:** the 2.1 block's `cash_out` already includes payouts. Proposed reading:
the 2.1 block's `cash_out` = cash out + drops + payouts (every non-refund cash that left), and
the `sales` block splits them (`cash_out`, `drops`, `payouts`). Both give the same
`expected_cash`; a test checks that.

## 5. X report (mid-session, read-only)

- `GET /cashier-sessions/{id}/x-report` (JSON) and `…/x-report/text?lang=&width=` (printable).
  Only an **open** session (`409 session_closed`: read the close report instead).
- At the till: the caller's own session, `session.view_expected` (overridable, `context_ref` =
  the session ID). Back office: any open session of a branch where the caller has `report.sales`
  and `session.view_expected`.
- Contents: everything in the close report (§4, 2.6 §10) as of now, with `expected_cash`, but no
  count and no over/short. Header "X REPORT — not a close", local time of the read.
- Not stored. Every read writes the audit entry `session.x_report` (who, approver), which the
  close report and Z count.

## 6. Z report (end of day per branch)

- **Run:** `POST /z-reports {day}` with `Idempotency-Key` (branch from the register token, or
  `branch_id` in the body in the back office). Needs `day.close` at the branch (overridable at the
  till, `context_ref` = `<branch_id>:<day>`).
- **Covers:** every **closed** session of the branch whose business day (local open date) is
  `day` and that is not yet in a Z (K14, K16).
- **Refused when:**
  - a session of that day is still open → `409 sessions_open` with their numbers (K15);
  - no closed session of that day is left without a Z → `409 nothing_to_close`;
  - `day` is after today's local date → `422 invalid_field` (`day`);
  - on HQ for a branch that is not this node's → `403 read_only_replica` (the Z belongs to the
    node that owns the sessions; HQ reads the synced copy).
- An earlier day may be closed later (catch-up); days are independent, in any order.
- **Contents** (one snapshot, stored as JSON plus headline columns):
  - header: branch, business day, number, run time, by whom (approver), supplementary flag;
  - sessions: number, register, cashier, open / close time, forced, opening cash, expected,
    counted, over/short, float kept, to safe, float difference;
  - per register subtotals, and branch totals of:
    - sales by tender type (count + amount), refunds by tender type;
    - gross sales, discounts (line, cart), net sales, cash rounding;
    - returns, post-voids, line voids, cart voids (count + amount), price overrides;
    - saved change, balance paid, balance payouts;
    - cash in / out per reason, drops, reversals;
    - drawer opens, X reads, cash outs missing a nota (as of the Z run);
    - over/short total, **cash to deposit** = Σ drops + Σ to safe;
    - tax summary per rate: base (DPP) and tax, sales minus returns (2.3, `core::tax`);
    - first and last sale number, sales count.
  - Post-voids and returns count in the session they were **paid** in (2.6 D10, §19 item 29),
    so a Z never changes after a later void.
- **Immutable:** a posted Z is never edited or recomputed. Reprint:
  `GET /z-reports/{id}/text?lang=&width=&copy=true` (COPY, audited `z_report.reprint`, needs
  `report.sales`).
- A session in a Z is marked with the Z's ID; its close report is unchanged.

## 8. Sync and events

- Cash movements and Z reports are created on the branch node (or standalone), never at HQ, and
  pushed in the outbox (`cash_movement.posted`, `cash_movement.photo_added`, `z_report.posted`).
  Offline selling and cash in/out keep working (plan §1). Photo bytes follow separately (§2a).
- Cash reasons: HQ writes, outbox `cash_reason.put`; a branch answers writes
  `403 read_only_replica`.
- WebSocket (branch audience): `cash.moved {session_id}` (a back-office session view refreshes),
  `day.closed {branch_id, day}`.

## 16. Readings (from K1)

Choices made while building `core::cash` where the spec was silent; change them here if wrong.

1. **Permissions.** `cash.drop` and `day.close` are appended to the end of the catalogue, without a
   limit and overridable at the till (§2, §6). The Owner role gets them from `seed_defaults` (it
   rewrites Owner on every start); the Manager grants and the Cashier `cash.out` limit are K2's
   migration.
2. **Reversal checks**, in this order: the target is of another session → `invalid_field`
   (`reverses`); the target is itself a reversal → `invalid_field` (`reverses`); already reversed
   → `already_reversed` (its `field` is `reverses`); no note → `invalid_field` (`note`). A
   reversal is allowed when the original's reason was archived since (it takes the original's
   reason; only new movements are refused an archived reason).
3. **Report lines per kind** (`cash_in`, `cash_out`, `drops`): `count` = movements that are not
   reversals; `amount` = their sum minus the reversals of that kind, i.e. what the kind did to
   the drawer. `reversals` has its own count and Σ amount. A reason line counts its originals,
   nets its amount and counts its reversals too. A reason missing from the names list prints its
   ID.
4. **Both blocks.** The cash movements enter the `sales` block as three netted events
   (`SessionEvent::CashIn`, `CashOut`, the new `Drop`; left out when 0) and `SalesSessionReport`
   gains `drops`. The 2.1 block's movements come from `core::cash::close_movements`, which turns
   cash out, drops and payouts into `Movement::CashOut`; the server's `movements::to_movements`
   now calls it.
5. **Missing nota** flags only the original cash out; a reversal (kind `out` reversing an `out`)
   is never flagged itself.
6. **Float kept** defaults to the opening cash capped at the counted cash (a short drawer) and
   never below 0; a negative typed float is `invalid_field` (`float_kept`) like one above the
   count. `opening_proposed` is stored only when the typed opening differs from the proposal; the
   float difference is `opening_cash − opening_proposed` (0 without one). The X shows the proposal
   and the difference too (they are known since the open).
7. **Z run check** order: `day` after today → `invalid_field` (`day`), then open sessions of the
   day → `sessions_open`, then `nothing_to_close`. Running the Z of today is allowed.
8. **Z figures.** Net sales = gross sales − line discounts − cart discounts (returns and post-voids
   are their own lines). Gross sales, the sales count, the first / last sale (by posting time,
   ties by number) and the tax lines come from the session's sale documents (`SessionSales`), not
   from the close report. The tax summary lists every rate including 0%, and subtracts the tax of
   the returns **and post-voids** paid in the session (both give money back for sold lines).
   Besides the §6 list the totals also sum opening cash, expected, counted, float kept and the
   float difference. Register subtotals are keyed by register code; the session list is in open
   order; a Z with `seq > 1` is supplementary. The missing-nota count is the one **as of the Z
   run** (`ZSession::missing_nota`), not the stored close figure, since a photo may be added after
   the close (§2a). Per-rate sums that overflow are `amount_overflow`, never clamped.
9. **Texts.** Labels are a new `CashLabel` enum (ID/EN like `sale::Label`, which is unchanged;
   "Kasir" is the register in Indonesian, as on receipts). "Large text" is
   `Printout::large`, the line indexes 2.11 prints double size: the slip's amount and the Z's cash
   to deposit. The payout slip uses the slip layout with the payout's reference as its number,
   the customer line and the balance after. Void, discount, override, saved-change and
   balance-paid lines with nothing in them are left out; the Z's session times are
   `dd/mm HH:MM`.

## 17. Readings (from K2)

Choices made while building the `db` layer (`crates/db/src/cash/`, migration
`20261119000001_cash`) where the spec was silent; change them here if wrong.

1. **Cash reasons** have both `active` (offered at the register) and `archived_at` (deleted), like
   tender types; the rules see a reason as active only when it is active and not archived
   (`CashReasonRecord::for_rules`). The seeded ones have fixed IDs …0401–…0406 in the order of
   `core::cash::SEED_REASONS`. The name is trimmed, 1–60 characters; the direction never changes
   once created (`invalid_field` `direction`); `sort` is any `i32`. Writes are audited and sent as
   `cash_reason.put` / `cash_reason.archive`. There is no hard delete at all, so "a reason in use is
   never deleted" needs no usage check.
2. **Posting re-checks** what the database relies on, after the server's `core` checks: the
   movement's session must be open, on its register and the poster's (`no_open_session`); a new in
   / out needs an existing, active, non-archived reason of its direction (`invalid_field`
   `reason`); a reversal needs a known target (`invalid_field` `reverses`), then the §16 reading 2
   order, and must copy the original's kind, amount and reason (`invalid_field` `reverses`). The
   unique `reverses` key catches a racing second reversal (retryable). Audit `cash_movement.post`,
   outbox `cash_movement.posted` with the whole movement.
3. **No foreign keys** from a movement or a Z to branches, registers, sessions, users or reasons
   (like sales); a photo references its movement.
4. **Photos** take a slot `photo_no` 1–3 under a unique key, so racing uploads never make a fourth
   (the loser retries and gets `photo_limit`). The same photo ID with the same movement and hash
   is an unchanged replay, with anything else a `conflict`; the same file under a new photo ID is
   a new photo (sharing one file on disk is K6's). Photo rows are append-only by trigger. Audit
   `cash_movement.photo` on `cash_movement:<id>`, outbox `cash_movement.photo_added`.
5. **What the close stores** besides the 2.1 report: `float_kept` and the close-time
   `missing_nota` count on the session (`record_close_cash`, once), and the reasons its report
   shows with their name, direction and sort as at the close (`cashier_session_reason`,
   `record_close_reasons`, once; migration `20261121000002_session_reasons`), since a reason can
   be renamed or re-sorted later. Everything else of §4 is recomputed from rows that no longer
   change after the close (documents, movements, and the `drawer.open` / `session.x_report` audit
   entries, which only an open session gets). A session closed before that migration has no
   stored reasons and shows the live names.
6. **Drawer opens and X reads** are counted from audit entries whose target is
   `cashier_session:<id>` (the X route of K3 must use that target, as `POST /drawer/open` does); a
   new index on `audit_log (target, action)` serves the count.
7. **Proposed float** is the `float_kept` of the register's last closed session by close time; a
   last session closed without one (before 2.7) proposes 0. `opening_proposed` is written once,
   while the session is open.
8. **The close report's two blocks** get the netted cash events (`cash::session_cash_events`)
   from K2 on, next to `sales::session_events`, which stays sales-only so that
   `core::cash::session_figures` (which takes the movements themselves) never counts them twice.
9. **Z storage:** the server's JSON snapshot plus headline columns from the branch totals
   (sessions, sales count, net sales, expected, counted, over/short, cash to deposit);
   `supplementary` = `seq > 1` by `CHECK`; append-only by trigger. Each covered session is linked
   by a guarded `UPDATE` (closed, of that business day and branch, in no Z); a guard that fails is
   a lost race (retryable). Audit `z_report.post`, outbox `z_report.posted` with the session IDs
   and the snapshot.
10. **Days still to close** (K18) are grouped by business day: a day is listed when it has a closed
    session in no Z, or when it is before today and has a session still open; each line counts its
    open and closed (unclosed) sessions. **Decided 2026-11-21 (option a): only days from the
    upgrade date onward are listed.** Migration `20261121000001_cash_since` adds
    `sales_settings.cash_since` (unix ms) and sets it to the time the migration runs: the upgrade
    of an existing install, or the first migration run of a fresh one (`NULL` would list every
    day). `GET /z-reports/pending` passes the branch-local day of it to `cash::pending_days`
    (`since`), which leaves out earlier business days. The Z run itself is not limited: an
    earlier day can still be closed by naming it (catch-up, §6), it is only not offered.
11. **`nota_flag_above`** is a column of the company's `sales_settings` row (default 100 000,
    `CHECK >= 0`). Until K6 adds it to `PUT /settings/sales`, that route keeps the stored value.
12. **Seeds:** a fresh install's `seed_defaults` also gives Manager `cash.drop` and `day.close`
    and Cashier `cash.out` ≤ Rp 50 000; the migration does the same for existing installs, the
    Cashier part only when Cashier has no `cash.out` grant (an edited limit stays).

## 18. Readings (from K3)

Choices made while building the server routes and the client (`crates/server/src/routes/
{cash,cash_reasons,cash_movements,cash_reports,z_reports}.rs`, `crates/client/src/cash.rs`,
`crates/client/src/fake/cash.rs`) where the spec was silent; change them here if wrong.

1. **The proposal** is read from a new `GET /registers/me/float` (`proposed_float`,
   `has_proposal`), since `GET /cashier-sessions/current` answers `404` when nothing is open.
   `SessionDto` gains `opening_proposed` and `float_kept`. The open's audit entry carries
   `opening_proposed` and `float_difference`.
2. **No proposal without a kept float:** `opening_proposed` is stored only when the register's
   last closed session kept a float (`cash::last_float_kept`). A register's first session, or the
   first after a session closed before 2.7, proposes 0 (§3) but flags no float difference:
   there is nothing to compare with.
3. **X permission:** `session.view_expected` is now overridable in `core` (K11 says so; K1 had
   left it out). At the till, the caller's own open session needs it (a manager approves,
   `context_ref` = the session ID); anyone else (the back office, or another user at the till)
   needs `report.sales` and `session.view_expected` at the session's branch, not overridable. The
   blind close of spec 2.1 §5 still only checks that it is held. An unknown session is `404`, a
   closed one `409 session_closed` before any permission check.
4. **The X counts itself:** the audit row `session.x_report` (target `cashier_session:<id>`, with
   `approved_by`) is written in the read's transaction before the figures, so `x_reports` of an X
   includes that read; the JSON and the text are each one read.
5. **Close report shape:** `CloseReportDto` gains `cash` (per kind and reason, reversals, drawer
   opens, X reads, missing notas) and `float` (`float_kept`, `to_safe`, `opening_proposed`,
   `float_difference`); its `sales` block gains `opening_cash` and `drops`. A stored report shows
   the missing-nota count stored at its close (0 for a session closed before 2.7) and a `null`
   float kept / to safe before 2.7; the client reads both blocks with serde defaults, so an older
   server's report still parses. In the close-report text and a Z, a session closed before 2.7
   counts 0 kept and 0 to the safe.
6. **`float_kept` at a close** is checked after the 2.1 checks (owner, register, still open) and
   before anything is written; a force close takes it the same way, default the opening cash
   capped at the count.
7. **Cash movement body:** a reversal may leave out `kind`, `amount` and `reason_id`; when sent
   they must be the original's (`422 invalid_field` `reverses`). The replay check comes first,
   so the same `PUT` after the session closed still answers `200`. The read model adds `effect`
   (the signed change to the expected cash). An unknown reason is `invalid_field` `reason`.
8. **Who reads movements:** one movement: its cashier, or `report.sales` at its branch. The list:
   the caller's own session (`cashier_session_id`), or `report.sales` at `branch_id` (without
   `branch_id`: at every branch), like the sales lists.
9. **Slips:** a copy is free when the movement's session is the caller's open session at the
   calling register; otherwise `sale.reprint` (overridable at a register, `context_ref` = the
   movement ID; required in the back office), audited `cash_movement.reprint`. The **payout slip**
   is read by any user session (like the balance), numbered by its balance entry ID, with the
   customer line "name · masked phone" and the balance after it (the sum of the customer's
   entries up to it in ID order); a copy follows the cash slip's rule, audited
   `customer.payout_reprint`. An unknown entry, or one that is not a payout of that customer, is
   `404`.
10. **Close report text:** its own cashier or `report.sales` at the branch; an open session has
    none (`404 not_found`). `copy=true` prints COPY and is not audited (the report is a read of a
    stored document, like `GET /cashier-sessions/{id}`).
11. **Z run:** `day` is `YYYY-MM-DD`; at a register the branch is the register's (another
    `branch_id` is `invalid_field`), in the back office `branch_id` is required. An HQ node always
    answers `403 read_only_replica` (it owns no sessions). Order: the day's format, the node, the
    branch, `day.close` (back office), then in the transaction the till's override
    (`context_ref` = `<branch_id>:<YYYY-MM-DD>`) and `core::cash::check_z_run`.
12. **Z reads:** `report.sales` at the Z's branch, or the user who ran it (a cashier who ran it
    with a manager's approval can show it); a copy of the text needs `report.sales` and is audited
    `z_report.reprint`. The list without `branch_id` needs `report.sales` at every branch.
13. **Z inputs:** each covered session's stored close (figures recomputed from rows that no
    longer change, its stored float) and its missing notas as of the run (§16 reading 8). The
    sales documents come from `cash::session_sales`: sales posted in the session (later voided ones
    too), Σ line gross, first / last by posting time; the tax of the sale lines as stored, minus
    the post-voids' lines as stored and the returns' lines through `core::tax::line_tax`
    (tax-inclusive, at the sold line's rate, no tax when it had none). **Decided 2026-11-21:** a
    return without a receipt has no sold line, so it takes the returned product's **current tax
    class** at the rate valid on the return's local day (0% when the class has no rate yet),
    tax-inclusive like the other returns and taxed when the company is tax-registered; every
    return counts in the tax summary.
14. **Z snapshot:** the stored `figures` is the `ZSnapshotDto` the API answers (number, day, seq,
    supplementary, run time, sessions, per-register and branch totals each with the summed `sales`
    and `cash` blocks); the text is rebuilt from it, never recomputed.
15. **Days still to close** need `report.sales` or `day.close` at the branch; a register's own
    branch by default, `branch_id` required in the back office.
16. **Events:** `cash.moved {session_id, movement_id, number, kind}` and `day.closed {branch_id,
    day, z_report_id, number}` on the branch audience; cash reason writes publish
    `catalog.changed {scope: "cash_reasons"}` so registers reload the list. A replay publishes
    nothing.
17. **Error codes:** `sessions_open` carries `sessions` (the numbers); `already_reversed` is `409`
    with `field: reverses`; `photo_limit` is mapped (`409`, `max`) though no route returns it until
    K6. The register maps the four codes to messages (`sessions_open` names the sessions); the
    screens come with K4 / K5.
18. **Cash reasons** are read with a user session or the device token alone (registers);
    `archived=true` needs `tender.manage` from any role assignment.
19. **Client:** the till's calls are on `Service` (reasons, movements, slips, payout slip, X,
    close text, proposed float, the Z run and text, pending days), the back office's on
    `BackOffice` (reason management, Z list and read, and `force_close_session`, which the client
    did not have yet). The fake keeps the rules through `core::cash` with one register, no photos,
    no events and no sales documents in a Z (see `crates/client/src/fake/cash.rs`).
