# 2.2 Catalog — spec

Status: draft 2026-11-08 (decisions below agreed; rules marked *(proposed)* await review).
Parent: `docs/plan.md` §2.2. Depends on 2.1 (HQ-owned master data, outbox, audit, permissions).

Decided 2026-11-08:
- Units of measure are defined **per product** (shared by all its variants).
- P1 product types: **stock, weighed (+ scale barcodes), service, bundle/kit**. Repack and
  batch/expiry/serial tracking are P2.
- A product has **at most 3 option attributes** (e.g. Size, Color, Material).
- **Per-branch assortment**: products are global, HQ can switch a product off for a branch.

## 1. Structure

```
Category (tree, max depth 4)      Brand      Tag
          │                          │         │
          ▼                          ▼         ▼
Product ── code, name, receipt name, type, tax class, base unit, flags, image
  ├── Option (≤3)    Size: S, M, L     Color: Red, Blue      (ordered values with short codes)
  ├── Unit (≥1)      pcs ×1 (base) · pack ×6 · box ×24       (shared by all variants)
  ├── Variant (≥1)   SKU, option values, PLU (weighed), archived
  │     └── Barcode*  (variant, unit) → code       unique company-wide
  ├── Bundle component*  (bundle type only) variant + unit + qty
  └── Branch block*  branch where this product is NOT sold
```

- **Every product has at least one variant.** A product without options has exactly one variant
  with no option values; the UI hides it and shows the product directly. Sales lines, stock
  movements and price-list entries always reference a **variant + unit**, never a product.
- **Prices are not part of the catalog.** They live in price lists (2.3), per variant + unit.
  **Cost is not part of the catalog** either; it is derived by inventory (2.8, moving average).
- Supplier links (preferred supplier, supplier item code) belong to purchasing (2.8).

## 2. Product

| Field | Rule |
|---|---|
| `code` | Product code, 1–24 chars `[A-Z0-9._-]`, **stored upper case**, unique. Generated if empty (§7). |
| `name` | Required, 1–120 chars, trimmed. |
| `receipt_name` | ≤32 chars for the 32/42-column receipt; defaults to `name` cut to 32. |
| `type` | `stock` · `weighed` · `service` · `bundle` (§5). Fixed once any variant has been used. |
| `category_id` | Optional; empty = "Uncategorised" in lists and reports. |
| `brand_id`, `tags` | Optional. Tags are free labels (≤20 per product) used for search and filters. |
| `tax_class_id` | Required. 2.2 seeds `Standard` and `Exempt`; rates and inclusive/exclusive rules are 2.3. |
| `base_unit` | The stock unit (§4). |
| `sellable` / `purchasable` | Defaults true / true (`service` and `bundle`: purchasable false). |
| `open_price` | Cashier types the price at the register (old Sultan `EDITABLE_PRICE`), e.g. "misc item". |
| `requires_note` | Register asks for a line note (old `REQUIRE_NOTE`), e.g. engraving text. |
| `tracking` | `none` in P1; `batch` / `serial` reserved for P2 (column exists now, other values rejected). |
| `image` | Optional, one per product (§8). |
| `archived_at` | Soft delete (§9). |

Search uses a `search_key` column: name + receipt name + code + brand, lower-cased with accents
removed, because text in the database compares byte-wise (2.1 decision).

## 3. Options and variants

- 0–3 **options** per product, in order. Each option has a name (`Size`) and an ordered list of
  **values**, each with a display name (`Medium`) and a short code `[A-Z0-9]{1,8}` (`M`).
- The variant grid is the cartesian product of the values. The user **switches off combinations
  they do not sell**: those variants are simply not created. Max 500 variants per product *(proposed)*.
- A variant's option values are unique within the product (no two "M / Red").
- **Variant SKU**: `[A-Z0-9._-]{1,32}`, upper case, unique company-wide. Default:
  `<product code>-<value codes joined by ->`, e.g. `KAOS01-M-RED`. A product with no options:
  SKU = product code. Editable.
- Variant display name: `<product name> – <values joined by " / ">`, e.g. `Kaos Polos – M / Red`.
- **After first use** (any sale, stock movement or price-list entry references a variant):
  - new values can still be added to an existing option (creates new variants on request);
  - values can be renamed, but **not removed**: archive the variants instead;
  - options can **not** be added or removed (create a new product instead).

## 4. Units of measure (per product)

- One **base unit** (the stock unit) plus up to 5 other units *(proposed)*. Each unit has a name
  (`box`), a **factor** to the base unit (`24`), `sellable` / `purchasable` flags, and a short
  display name for the receipt.
- Unit kinds: **integer** (`pcs`, `box`) or **decimal** (`kg`, `liter`). The base unit's kind decides
  how quantities are entered: integer → whole numbers only, decimal → up to **3 decimal places**.
  Quantities are stored as fixed-point `i64` thousandths everywhere (`Qty(i64)`, 1.000 = 1000).
- Factor rules: factor > 1 for non-base units; when the base unit is integer, factors are whole numbers.
  Unit names are unique per product.
- One **default sale unit** and one **default purchase unit** (e.g. sell `pcs`, buy `box`).
- Conversion: `base_qty = qty × factor`. A sale of 2 box records unit `box`, qty 2, base qty 48.
- **After first use** a unit's factor and the base unit are fixed. To change packaging, archive the
  unit and add a new one (e.g. `box(20)` replaces `box(24)`).
- Common unit names come from a company **unit list** (pcs, box, pack, renteng, kg, gram, liter…)
  for autocomplete; the product stores its own copy, so editing the list never changes products.

## 5. Product types

### stock
Normal item. Every sale/receipt moves stock in the base unit.

### weighed
- Base unit must be **decimal** (`kg` by default). **No other units** (packs of a weighed item are a
  separate `stock` product, or repack in P2).
- Each variant may have a **PLU**: numeric, 1–6 digits, unique among weighed variants. The scale and
  the scale-barcode layouts use it.
- At the register, quantity comes from a scale barcode (§6), manual weight entry, or (P2) a
  connected scale.

### service
No stock, no cost (margin = price). Can have units (`hour`). Not purchasable by default.

### bundle (kit)
- Has its **own price** (2.3) and its own barcodes, **no stock of its own**, **no options**
  (exactly one variant) and only its base unit (`pcs`, integer).
- **Components**: 1–50 lines of (variant, unit, qty > 0). Components are `stock`, `weighed` or
  `service` variants of **other** products — **no bundles inside bundles**, no archived variants,
  no duplicates of the same variant + unit.
- Selling 1 bundle posts stock movements for each component (`qty × factor`, in base units).
  Available bundles = min over components of ⌊stock / required⌋ (informational only).
- The sale line keeps a **snapshot of the components** at sale time, so editing a bundle later never
  changes past sales, returns or reports. Returning a bundle returns its snapshot components.
- Revenue is split over components for margin reports in proportion to each component's default
  price × qty at sale time *(proposed; implemented with 2.6/2.10)*.

## 6. Barcodes and lookup

### Barcodes
- A barcode belongs to one **variant + unit** (`8991234567890` → Aqua 600ml pcs, `18991234567897` →
  same variant, unit box). A variant + unit may have **any number** of barcodes.
- Code: 1–64 printable ASCII chars, no spaces, stored as scanned (digits, or letters for Code-128).
- **Unique company-wide** among non-archived variants. Archiving a variant frees its barcodes
  only after they are removed explicitly (keeps old scans resolvable for returns) *(proposed)*.
- EAN-13 / EAN-8 / UPC-A check digits are validated when the code is all digits and that length;
  a mismatch is rejected unless `allow_invalid_check_digit` is set (importer, odd vendor codes).

### Scale barcodes
- Company setting: a list of **layouts**, each one EAN-13:
  `prefix (2 digits, 20–29) · PLU (n digits) · value (m digits) · check digit`, with
  `2 + n + m = 12`, and a value kind: **weight** (grams) or **price** (Rupiah).
  Defaults *(proposed)*: `21 PPPPP WWWWW C` (weight) and `22 PPPPP $$$$$ C` (price).
- Prefixes of layouts must not overlap each other or the internal barcode prefix (§7).
- Decoding: weight → qty = grams / 1000 kg. Price → line amount = embedded price exactly, and
  qty = price / unit price rounded to 3 dp (how membership prices treat price-embedded labels is
  settled in 2.3). Weight or price of 0 → rejected (`scale_value_zero`). Bad check digit → not a scale code.

### Lookup at the register — `GET /catalog/lookup?code=…`
Order, first match wins:
1. **Exact barcode** (including old/imported codes that happen to start with a scale prefix).
2. UPC-A/EAN-13 normalisation: 12 digits → try `0` + code; 13 digits starting with `0` → try without.
3. **Scale barcode** layouts (prefix match + valid check digit) → PLU → variant + quantity/amount.
4. **SKU** (upper-cased input).
5. **PLU** when the input is 1–6 digits and step 1–4 found nothing.

Result: variant, unit, qty (default 1 or from the scale code), optional embedded amount, and flags
(`open_price`, `requires_note`, `type`). Errors: `not_found`, `archived`, `not_sold_here`
(branch block, §10), `not_sellable`.
Name search for the register and back office: `GET /catalog/search?q=` (prefix/contains on
`search_key`, paged, max 50 per page).

## 7. Code generators

- **Product code**: `<prefix><counter>`, prefix default `P`, counter zero-padded to 6 → `P000123`.
- **Internal barcode** (for items without a manufacturer barcode): EAN-13 with prefix `29`
  (configurable, must not be a scale prefix): `29` + 10-digit counter + check digit.
- Counters live at HQ (only HQ writes the catalog, so there are no conflicts between branches).
  A generated value that is already taken (e.g. imported) is skipped.

## 8. Categories, brands, tags, images

- **Category tree**: name, short code, parent; max depth 4; moving a category is allowed, cycles are
  rejected; names unique among siblings. Archiving a category hides it from pickers only; products keep it.
- **Brands**: name (unique), archived.
- **Tags**: free text on the product, lower-cased, used for filters.
- **Images**: one per product, optional. The server resizes to max 512×512, stores WebP/JPEG
  ≤256 KB **in the database** (so it syncs to branches with the rest of the catalog and is
  covered by backups). Used by the back office and (later) the quick-key grid.

## 9. Archive, never delete

- Products, variants, units, barcodes, categories and brands are **archived**, never deleted, once
  anything references them. A never-used row may be hard-deleted (e.g. a typo right after creation).
- Archived variants cannot be sold, bought, or added to bundles, but appear in history, returns
  and reports. Archiving a product archives all its variants.
- Unarchive is allowed when the barcodes/SKU are still free.

## 10. Branch assortment

- By default a product is sold at **every branch**. HQ can **block** it for selected branches
  (`product_branch_block(product_id, branch_id)`).
- At a blocked branch: lookup returns `not_sold_here`, search hides it, purchase orders for that
  branch warn. History, stock (if any) and reports still show it. Transfers of remaining stock out
  of the branch are still allowed.

## 11. Permissions, sync, events

- New permissions: `catalog.manage` (HQ only: products, variants, units, barcodes, categories,
  brands, assortment, generator settings, scale layouts) and `catalog.view_archived`.
  Reading the catalog (lookup, search, list) needs any user session **or** a device token.
  Seed: Owner + Manager get `catalog.manage`; Stock clerk gets it too *(proposed)*.
- Writes are HQ-only (`403 read_only_replica` on branch nodes), audited, and append an outbox row in
  the same transaction, like 2.1.
- WebSocket event `catalog.changed {product_id}` so registers drop cached lookups.

## 12. REST resources (`/api/v1`)

| Resource | Read | Write |
|---|---|---|
| `PUT/GET /products/{id}` (product + options + units + variants + barcodes + components in one document) | session/device | `catalog.manage` |
| `GET /products?q=&category_id=&brand_id=&type=&archived=&before_id=` | session/device | – |
| `POST /products/{id}/archive`, `/unarchive` | – | `catalog.manage` |
| `PUT/GET /products/{id}/branch-blocks` (full set of blocked branch ids) | session | `catalog.manage` |
| `PUT/GET /categories/{id}`, `GET /categories` (tree) | session/device | `catalog.manage` |
| `PUT/GET /brands/{id}`, `GET /brands` | session/device | `catalog.manage` |
| `PUT/GET /products/{id}/image` (binary) | session/device | `catalog.manage` |
| `GET /catalog/lookup?code=`, `GET /catalog/search?q=` | session/device | – |
| `GET/PUT /settings/catalog` (code prefixes, scale layouts, unit list) | session | `catalog.manage` |
| `POST /catalog/generate/{product-code\|barcode}` | – | `catalog.manage` |

The product is written as **one document** (`PUT /products/{id}`) with client-generated UUIDv7s for
variants, units and barcodes, so the form saves atomically and a replay is idempotent. The server
validates the "after first use" rules by diffing against the stored version.
New error codes: `duplicate_barcode`, `duplicate_sku`, `duplicate_code`, `invalid_check_digit`,
`frozen_after_use` (with the field), `bundle_nesting`, `invalid_unit_factor`, `not_sold_here`,
`scale_prefix_overlap`, `scale_value_zero`.

API decisions (decided in C3):
- **JSON conventions**: quantities and unit factors are integer thousandths in fields named
  `*_thousandths` (`factor_thousandths: 24000` = ×24, `qty_thousandths: 500` = 0.5); money is
  integer minor units; times are unix ms; IDs are UUID strings. Empty `code` → generated (new
  product) or kept; empty variant `sku` → `<code>-<value codes>`.
- **Responses**: `PUT /products/{id}`, `/categories/{id}`, `/brands/{id}` answer `201` on create and
  `200` on update **and** on an unchanged replay (same body, nothing written). Product responses add
  `used`, `archived_at`, `archived_barcodes`, `created_at`, `updated_at`. `PUT …/branch-blocks` and
  `PUT /settings/catalog` always answer `200`. `POST …/archive|unarchive` answer the product (`200`).
- **Errors**: rule failures are `422` with `code` (the first failure), `field` and `errors`
  (every failure as `{code, field?, message}`); duplicates are `409` with `product_id`,
  `variant_id` (null for a product code) and `value`. Lookup: `404 not_found`, `422 archived` /
  `not_sold_here` / `not_sellable` / `scale_value_zero`. Images: `422 invalid_image`,
  `413 payload_too_large` (over 10 MB). Back-office lookup for a branch the user is not assigned
  to: `403 branch_not_assigned`.
- **Permissions**: `catalog.manage` and `catalog.view_archived` count only when held through a role
  assigned for **all branches** (the catalog is company-wide; a grant at one branch, e.g. the
  seeded Manager at JKT01, is not enough). `GET /products/{id}` of an archived product,
  `GET /products?archived=true` and `include_archived=true` on `/categories` and `/brands` are
  `403 permission_denied` without `catalog.view_archived`; a device token never has it.
  `GET /settings/catalog` and `GET …/branch-blocks` need a session; the other reads accept a device
  token alone.
- **Assortment at lookup/search**: the branch comes from the device token's register (a PIN session
  at a register included), never from the query. A back-office session may pass `branch_id` (one of
  its branches); without it no assortment applies. The response's `branch_id` says which applied.
- **Search** returns up to `limit` (1–50, default 20) hits without a cursor.
- **Images** are stored as JPEG (quality 85, lowered to 35 and then shrunk until ≤256 KB); `GET`
  sends an `ETag` and honours `If-None-Match` (`304`). `DELETE …/image` answers `204`.
- **Writes** run in one transaction and are retried after a lost race (a uniqueness race, a
  `MySQL` deadlock / lock wait timeout, a busy `SQLite` database): at most 5 attempts, with a
  jittered backoff of at most 5, 10, 20 and 40 ms before the 4 retries; when all 5 lose, the
  answer is `409 conflict` (never `500`). Every write that changed something sends
  `catalog.changed` to **every** event socket with `scope` (`product` / `category` / `brand` /
  `settings`) and the entity ID (`product_id`, …).
- `GET /tax-classes` (session/device) lists the seeded tax classes for the product form.

## 13. Old Sultan import (mapping)

- `items` row → product (`type` from flags: `SERVICE` → service, `PACKAGE` → bundle, else stock) with
  one variant; old `barcode` → SKU (upper-cased, sanitised) **and** a barcode on the base unit.
- `barcode_link` + `count_link` (box item link) → a unit `box(count_link)` on the linked product,
  with the box item's barcode on that unit; the box item itself is not created as a product.
- `unit` text → base unit (`kg`/`gram`/`liter` → decimal, else integer); `categories` tree →
  categories; `picture` file → image if readable.
- Flags: `EDITABLE_PRICE` → `open_price`, `REQUIRE_NOTE` → `requires_note`, `SELLABLE` →
  `sellable`, `PURCHASE` → `purchasable`. `sellprices` → Default price list with quantity tiers (2.3).
  `buy_price` → opening cost (2.8). Barcode check digits are not validated on import.
- The importer prints a report of every item it could not map cleanly.

## 14. Test cases

`core` (table-driven):
1. Variant grid: 2 options (3 × 2) with one combination switched off → 5 variants; SKUs `CODE-M-RED`…
2. No options → exactly one variant, SKU = product code.
3. 4th option → rejected; duplicate option-value combination → rejected.
4. Unit factor: integer base + factor 2.5 → rejected; decimal base + 2.5 → ok; factor ≤ 1 → rejected.
5. Qty: 1.5 on an integer unit → rejected; 0.125 kg ok; 0.1255 → rejected (3 dp).
6. Conversion: 2 box(24) → base 48; 0.250 kg → 250 thousandths.
7. EAN-13/EAN-8/UPC-A check digit valid/invalid; non-numeric code skips validation.
8. Scale weight `21 00123 01250 C` → PLU 123, 1.250 kg. Price `22 00123 15000 C` → amount 15 000.
   Wrong check digit → not a scale code. Value 0 → `scale_value_zero`.
9. Scale layout validation: lengths not adding to 12, prefix outside 20–29, overlapping prefixes,
   overlap with the internal barcode prefix → rejected.
10. Lookup order: exact barcode beats scale parse; UPC-A ↔ EAN-13 normalisation; SKU case-insensitive
    input; PLU fallback only for short numeric input.
11. Bundle: nested bundle → `bundle_nesting`; archived component → rejected; selling 2 bundles of
    (1 pcs A + 0.5 kg B + 1 box(6) C) → base movements A −2, B −1.000, C −12.
12. Frozen after use: removing an option value, adding an option, changing a unit factor, changing
    the type or base unit → `frozen_after_use`; renaming → allowed; adding a value → allowed.
13. Category tree: cycle → rejected; depth 5 → rejected; duplicate sibling name → rejected.
14. Generators: next product code skips taken values; internal EAN-13 has a valid check digit and
    never uses a scale prefix.

Server (HTTP, SQLite + MySQL):
15. `PUT /products/{id}` create → replay → no duplicates; update diff applied atomically.
16. Duplicate barcode / SKU across products → 409 with the conflicting variant.
17. Branch node → `read_only_replica`; user without `catalog.manage` → `permission_denied`.
18. Lookup with a device token at a blocked branch → `not_sold_here`; at another branch → found.
19. Archive product → lookup `archived`, search hides it, `GET /products?archived=true` shows it.
20. Every catalog write produces one audit row and one outbox row in the same transaction.
21. Image upload: >512 px is resized; non-image → 422.
22. `catalog.changed` event reaches a connected register after a product write.

## 15. Implementation phases (proposed)

| Phase | Content |
|---|---|
| **C1 `core::catalog`** | `Qty`, unit/factor rules, variant grid, SKU/code rules, EAN check digits, scale layouts + decoding, lookup resolution (pure, over a trait), bundle validation + explosion, "frozen after use" diff. Target ≥95%. |
| **C2 `db`** | Migrations (SQLite + MySQL) for categories, brands, products, options, values, units, variants, barcodes, bundle components, branch blocks, images, catalog settings, counters; repositories; `catalog.*` permissions in seed roles. |
| **C3 `server`** | Endpoints in §12, lookup/search, image resize, events, OpenAPI + Postman requests. |
| **C4 UI (back office)** | First back-office window: login with password, product list + product form (tabs General / Variants / Units & barcodes), category and brand editors, using the `client` `Service` trait + headless tests. |
| **C5 Register lookup** | Barcode field on the register screen resolves through `/catalog/lookup` (shows the item; the real cart arrives with 2.3 + 2.6). |

The old-Sultan importer (§13) is built later as its own phase, once pricing (2.3) and stock (2.8) exist.

## 16. Out of scope / later

Repack (P2) · batch/expiry and serial tracking (P2, column reserved) · shelf label and barcode printing
(P2, 2.11) · multiple images per product/variant · per-variant units · per-branch product fields
(e.g. local receipt name) · supplier item codes (2.8).
