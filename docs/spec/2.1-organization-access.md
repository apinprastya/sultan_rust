# 2.1 Organization & access — spec

Status: agreed 2026-11-07; amended 2026-11-08 (branch time zone, session numbers, past session reports). Parent: `docs/plan.md` §2.1.

## 1. Structure

```
Company (exactly one per install, for now)
└── Branch            code (JKT01), name, address, NPWP, receipt header/footer, time zone
    ├── Register      code (R2), default stock location, device token
    └── Stock location  e.g. store floor, warehouse; one is the default receiving location
```

- Branch code and register code appear in document numbers: `JKT01-R2-261107-0001`.
- Every branch has an IANA **time zone** (default `Asia/Jakarta`; e.g. `Asia/Makassar`,
  `Asia/Jayapura`), set by `sultan init --timezone` and `PUT /branches/{id}`. The date in a
  document number is the **branch-local** date of the document (decided 2026-11-08).
- Moving stock between locations of the same branch is an internal transfer (no shipping step, no HQ).
- Master data in this section (branches, registers, locations, users, roles) is **HQ-owned**.
  Branch nodes hold a read-only replica and answer writes with `403 read_only_replica`.
  In `standalone` mode the node is HQ, so this has no effect.

## 2. Register identity

The machine is an identity of its own, separate from the cashier logged in on it.

- **Pairing:** an admin creates the register in back office → the server issues a one-time
  **pairing code** (valid 10 minutes, single use). The setup wizard on the machine calls
  `POST /api/v1/registers/pair {code}` → receives a long-lived **device token**.
  Only the SHA-256 hash of the token is stored on the server. **Unpairing** revokes the token.
- Every register request sends `X-Register-Token`. The server derives `register_id` and `branch_id`
  **from the token only**; a `branch_id`/`register_id` in a request body is ignored.
- A revoked or unknown device token → `401`, even when the user session is valid.
- Every document records: `branch_id`, `register_id` (null for back-office documents such as a PO),
  `user_id`, `cashier_session_id` (register sales, returns, cash in/out, drawer open) and
  `approved_by` (when a manager override was used).

## 3. Permissions & roles

- **Permission catalog is fixed in code** (`core::access::Permission`), each with a stable string key.
- Some permissions carry a **limit**: `MaxPct` (basis points) or `MaxAmount` (money). Initial set:

| Key | Limit | Meaning |
|---|---|---|
| `sale.create` | – | sell at the register |
| `sale.discount` | MaxPct | line discount |
| `sale.cart_discount` | MaxPct | whole-cart discount |
| `sale.void_line` / `sale.void` / `sale.post_void` | – | voids |
| `price.override` | – | manual price at the till |
| `refund.with_receipt` | – | return by receipt lookup |
| `refund.no_receipt` | MaxAmount | return without receipt |
| `cash.in` / `cash.out` | MaxAmount (out) | petty cash |
| `drawer.open` | – | open drawer without a sale |
| `session.open_close` | – | open/close own cashier session |
| `session.view_expected` | – | see expected cash before/while counting |
| `session.force_close` | – | close someone else's abandoned session |
| `user.manage` / `role.manage` | – | HQ only |
| `org.manage` | – | branches, registers, locations, pairing (HQ only) |
| `user.unlock` | – | unlock a locked-out user |
| `stock.adjust` | – | stock adjustments |
| `report.sales` / `report.profit` | – | reports |
| `audit.view` | – | audit log viewer |

  The catalog grows with later sections; adding a permission is a code change + migration of seed roles.
- **Roles are data**: name + set of (permission, optional limit).
- **Grants only add, never deny.** Effective permissions of a user at a branch = union of the roles
  assigned for that branch or for "all branches". For the same limited permission, the **highest limit wins**.
- **Assignment:** (user, role, branch | all branches).
- Reports and lookups only show branches the user is assigned to.
- **Seeded roles:** Owner (all permissions, no limits; cannot be deleted or emptied), Manager, Cashier,
  Stock clerk, Viewer (editable).
- **Invariant:** at least one active user holds Owner for all branches. Any change that would break
  this is rejected.
- Permission checks happen **on the server**. The UI hides actions only as a convenience.

## 4. Authentication

| Where | How | Session |
|---|---|---|
| Register | lock screen shows the branch's users (`GET /registers/me/users`) → pick name → PIN (`POST /auth/pin`) | bound to (user, register) |
| Back office | username + password (`POST /auth/password`) | no register |

- PIN: 4–6 digits. Password: min 8 characters. Both hashed with **argon2id**.
- Session token: opaque, 32 random bytes (base64url), only the hash is stored (instant revocation,
  works offline). Idle expiry (setting); register auto-locks after N idle minutes (per-branch setting).
  Locking does not end the cashier session.
- **Lockout:** 5 consecutive failures → that user is locked on that branch for 5 minutes, or until
  someone with `user.unlock` unlocks them. A successful login resets the counter.
- Users/roles are edited **only at HQ**. Branches authenticate against their replica, so login works
  while HQ is offline. Changes arrive by sync and apply on the next request of open sessions.
- `POST /auth/logout` revokes the session and pushes `session.revoked` on the events WebSocket.

## 5. Cashier session

Login says *who is at the register*; the cashier session says *whose money is in the drawer*.

- **Open:** `POST /cashier-sessions {opening_cash}` → bound to (user, register). Number:
  `<BRANCH>-<REGISTER>-S-<YYMMDD>-<NN>`, e.g. `JKT01-R2-S-261107-01` (decided 2026-11-08):
  - the date is the session's open time in the **branch local time zone** (§1), so a session
    opened at 00:30 WIB is dated that day even though UTC is still on the previous one;
  - `NN` is a per-register, per-local-day sequence starting at `01`, printed with at least two
    digits; the 100th session of a day is `…-100` (it grows, it never fails);
  - the number is allocated in the open transaction; a unique index on (register, local day,
    sequence) keeps it unique when two opens race (the loser is retried and gets the normal
    `409 session_already_open`). A lost race (that unique index, a `MySQL` deadlock / lock wait
    timeout, a busy `SQLite` database) is retried at most 5 attempts in all, with a jittered
    backoff of at most 5, 10, 20 and 40 ms before the 4 retries; when all 5 lose, `409 conflict`.
- **Rules:** at most one open session per register and one per user. Selling, refunds, cash in/out and
  drawer open require an open session of the logged-in user on this register → otherwise `409 no_open_session`.
  Lock/break keeps the session open.
- **Handover:** cashier A closes (counts, gets report), cashier B opens a new session. No shared sessions.
- **Blind close:** `POST /cashier-sessions/{id}/close {counted_cash, counts?}`. The cashier enters the
  count (optionally per denomination) **before** seeing anything. The response is the **close report**:
  - `expected_cash = opening_cash + cash_sales − cash_refunds + cash_in − cash_out`
  - `over_short = counted_cash − expected_cash`
  - totals per tender, number of transactions, voids, discounts, overrides used.
  Printed on the receipt printer and stored. Users with `session.view_expected` can see expected cash live.
- **Past sessions and reports:** `GET /cashier-sessions/{id}` returns the session and, once
  closed, its **stored** close report exactly as the close returned it, plus what a printout
  needs (session number, branch and register codes and names, time zone, cashier and forcing
  manager names). `GET /cashier-sessions` lists sessions (filters `branch_id`, `register_id`,
  `user_id`, `status` = `open`/`closed`, `from`/`until` on the open time; paging `limit` +
  `before_id` → `next_before_id`, like `/audit`). A cashier reads their own sessions; anyone
  else needs `report.sales` at the session's branch. While a session is open, `expected_cash`
  stays hidden unless the caller holds `session.view_expected` (blind close); a closed report
  shows everything to anyone allowed to read it.
- **Reprint** of a close report (later) uses `GET /cashier-sessions/{id}`; the stored report is
  complete for it, no recomputation.
- A close cannot be undone; corrections are separate manager adjustment entries (audited).
- **Force close** (`session.force_close`): a manager closes an abandoned session (crash, cashier left);
  audited, report marks it as forced.
- Cash in/out, X report and daily Z report: detailed in §2.7.

## 6. Manager override

- When a check returns `NeedsOverride`, the register opens the override dialog. The manager picks
  their name and enters their PIN → `POST /overrides {action, value, context_ref, approver_id, approver_pin}`.
- Result: a **single-use override token** bound to (action, value, register, context_ref), short TTL (2 min).
  The client sends it as `X-Override` with the action request; the server consumes it.
- Approver must hold the permission with a high enough limit **at this branch**, and must not be the requester.
  Wrong PIN counts towards the approver's lockout.
- Audit: requester, approver, action, requested value, register, document.

## 7. Audit log

Append-only. Every write in this section (org, users, roles, assignments, pairing/unpairing, unlock,
override, session open/close/force-close, login failures/lockouts) is logged with: time, branch,
register, user, action, target, before/after (JSON).

## 8. REST resources (`/api/v1`)

| Resource | Read | Write |
|---|---|---|
| `/branches`, `/registers`, `/locations` | `org.manage` or assigned branch | HQ only, `org.manage` |
| `/registers/{id}/pairing-code`, `/registers/{id}/unpair` | – | HQ only, `org.manage` |
| `/registers/pair` | – | pairing code |
| `/registers/me/users` | device token | – |
| `/users`, `/roles` | `user.manage` / `role.manage` | HQ only |
| `/permissions` | any user (catalog) | – |
| `/auth/pin`, `/auth/password`, `/auth/logout` | – | – |
| `/users/{id}/unlock` | – | `user.unlock` |
| `/cashier-sessions`, `/cashier-sessions/current`, `…/{id}/close`, `…/{id}/force-close` | session | see §5 |
| `GET /cashier-sessions`, `GET /cashier-sessions/{id}` (past sessions, stored close report; reprint later) | own sessions, or `report.sales` at the session's branch | – |
| `/overrides` | – | see §6 |
| `/audit` | `audit.view` | – |
| `/events` (WebSocket) | session | – |

Master data uses `PUT /resource/{uuid}` (client-generated UUIDv7, idempotent). Errors are problem+json
with codes such as `read_only_replica`, `permission_denied`, `needs_override`, `locked_out`,
`no_open_session`, `session_already_open`, `last_owner`.

## 9. Test cases

`core` (table-driven):
1. Cashier limit 10%, requests 15% → `NeedsOverride`; manager limit 20% approves → allowed.
2. Same, manager limit 12% → rejected with the limit in the error.
3. Requester approves their own override → rejected.
4. Manager@JKT01 + Cashier@BDG01, logged in at BDG01 → Cashier permissions only.
5. Roles with 5% and 10% for the same permission → 10%.
6. Remove/deactivate/unassign the last active Owner → rejected.
7. 6th wrong PIN → locked; unlocked after 5 minutes or by `user.unlock`; success resets the counter.
8. Expected cash / over / short with mixed tenders, cash in/out, refunds.
9. Second open session on the same register or for the same user → rejected.
10. Sale without an open session → `no_open_session`.

Server (HTTP, SQLite + MySQL):
11. Pairing: happy path; expired code; reused code.
12. PIN login binds the session to the register; revoked device token → 401 with a valid session.
13. `branch_id` in a request body differs from the token → the token wins.
14. Branch node rejects user/role writes with `read_only_replica`.
15. Override token reused, or used for another value/document/register → rejected.
16. Blind close: expected cash hidden unless `session.view_expected`; close report numbers correct.
17. Replaying the same `PUT` → no duplicate row; replaying `POST` with the same `Idempotency-Key` → same response.
18. Logout from one session → WebSocket client receives `session.revoked`.
